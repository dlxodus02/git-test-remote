# Collaboration Convention

## 브랜치 네이밍

- 기능 개발: `feature/<task-name>`
- 버그 수정: `fix/<task-name>`
- 긴급 수정: `hotfix/<task-name>`
- 문서 작업: `docs/<task-name>`

브랜치 이름은 짧고 의미 있게 작성합니다.

## 커밋 규칙

- 한 커밋에는 하나의 의도를 담습니다.
- 리팩터링과 기능 추가를 가능하면 분리합니다.
- 리뷰어가 이해할 수 있는 메시지를 사용합니다.

예시:

```text
feat: 주문 생성 API 추가
fix: Redis 연결 재시도 로직 보완
docs: ERD 링크 추가
```

## 코드 리뷰 규칙

- 리뷰는 사람보다 코드에 집중합니다.
- 변경 이유와 영향 범위를 먼저 확인합니다.
- 동작 변경이 있다면 테스트나 재현 방법을 함께 남깁니다.
- 승인 전 반드시 궁금한 점을 해소합니다.

## PR 작성 규칙

- 제목만 봐도 변경 목적이 드러나게 작성합니다.
- 본문에 배경, 변경 내용, 테스트 결과를 적습니다.
- 스크린샷이나 API 예시가 있으면 함께 첨부합니다.

## 문서화 기준

- API 변경 시 명세를 함께 수정합니다.
- 정책이나 운영 절차가 바뀌면 `docs/`에 반영합니다.
- 구두로만 공유된 내용은 레포 문서로 남깁니다.
